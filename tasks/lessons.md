# Lessons（每次被纠正 / 自查出错后追加，不删旧条目）

## L1 评审外部方案前，先核查数值，再下结论

**事件**：审议 `~/.cursor/plans/g0-g5_bring-up_plan_5863fe07.plan.md` 时，我打算把对方硬写的
`DDL_PMU_PVD_THRESHOLD_3` 与 `DDL_PMU_PVD_FILTER_LENGTH_3200` 判为"臆造数值"。
实际核查后发现两个值**都是对的**（用户手册 `PVDTHSEL=010` → 2.7/2.8 V；50 µs @ 64 MHz = 3200 cycles，
与 aurora 自己的 `#if` 链完全吻合）。

**规则**：
- 反驳外部方案的**具体寄存器值/枚举/引脚**之前，必须先在数据手册或用户手册里找到对应表格，
  拿到页码/表号再开口。凭印象反驳一次就足以毁掉整份评审的可信度。
- 若核查后发现数值正确但**做法**仍有问题（如硬写枚举造成双真源），把反驳**收窄到做法**，
  并在对话里明确说出"我原本的预判错了"，不要悄悄改口。

## L2 "参考 XXX 工程"必须全库搜调用点，不能只看同名文件

**事件**（历史）：ESP32 息屏逻辑分散在 `ui.c`（LVGL 页面）与 `drv_gui.c`（背光 PWM），
只读 `ui.c` 导致误改背光。

**规则**：先 `Grep` 找全部相关调用点（含中断、初始化、配置表），确认哪些文件真正承担核心角色，再动手。
同名不代表逻辑全在其中。

## L3 交叉工程移植前，先 diff 两边的 SDK/DDL 库

**事件**：aurora 与 mppt-charger-300w 的 DDL 库版本分叉约 20 处 API 差异，
其中 `ATMR_CR1_UDISEN` 在两库中是 **bit1 vs bit2** —— 编译能过，行为静默错误。

**规则**：
- diff 时必须 `diff --strip-trailing-cr -w`，否则 CRLF/LF 差异会把每个文件报成"全文不同"，掩盖真实分歧。
- 位定义/结构体字段顺序类差异 → 标为"必须对着目标头文件重写"，禁止逐行照抄。

## L4 Windows 中文路径下用 Python 而非 shell 处理文件

**规则**：遇到中文路径，改用 Python `glob.glob()` + `pymupdf` 直接读写，绕过 shell 编码层。

## L5 中文注释里的路径通配符会构成嵌套注释

**事件**：G1 移植时在 `driver.h` 的块注释里写了「只有 `driver/src/*.c` 允许出现 DDL_ 前缀」，
`/` 紧跟 `*` 即 `/*`，ARMCC 报 `#9-D: nested comment is not allowed`。因该文件被三个 `.c`
包含，一处笔误直接造成 3 个编译错误，浪费了 Jovi 一次 Rebuild。

**规则**：
- 块注释 `/* */` 内**禁止**出现 `路径/*.c`、`目录/*` 这类通配符写法，也禁止出现 `*/`。
  改用「driver 层的 .c 文件」「driver\src 下的 .c」或行注释 `//`。
- 交付前对新建/修改的所有 `.c`/`.h` 跑一遍块注释状态机扫描（逐字符跟踪 `/*` `*/` `//`），
  这类错误无法靠肉眼通读可靠发现，但一段脚本 10 秒就能全量排查。
- 更一般地：**我无法运行目标工具链时，凡是能用脚本机械验证的性质就必须用脚本验证**，
  不能只依赖阅读。已验证有效的两类：块注释扫描、调用点与头文件声明逐一比对。

## L6 Edit 工具的 old/new 参数颠倒
**事件**：本次代码风格重构中两次把**新名字**填进 `old_string`（先是 `DRV_SYSTEM_PVD_THRESHOLD_SEL`，
后是 `BSP_ADC_CHANNEL_COUNT`），工具返回 "String to replace not found in file"。另有一次把
占位符文本当成替换内容写进了 `bsp_adc.c` 的 include 行，立刻自查才发现。
**规则**：
- 做**改名**时，`old_string` 永远是仓库里**当前存在**的那个名字，`new_string` 是目标名字。
  下手前先默念一遍"我要把 A 换成 B"，再确认 A 在 old 位、B 在 new 位。
- 批量改名优先用 `replace_all: true` 的**裸 token 替换**，一次一个 token，不要拼上下文——
  上下文越长越容易把新旧写串。
- 替换内容里**禁止**出现 `XXX_PLACEHOLDER` 之类的临时占位符。需要分两步时，
  第一步就写最终内容；实在要占位，必须在同一轮内立即补完并复查该行。
- 改名收尾必须跑"旧前缀零残留"脚本扫描，不能靠逐个 Edit 的返回值来确认改全了。

## L7 删除聚合头前必须先算出每个 .c 的真实符号来源
**事件**：删除 `driver.h` / `g32f031_device_cfg.h` 两个聚合头时，4 个 legacy `bsp_*.c`
原本靠聚合头间接拿到 12 个 DDL 头。若只按"文件名像什么"补 include，必然漏。
**规则**：
- 删聚合头之前，先建**符号 → 头文件**索引，只信"归属头文件集合大小为 1"的符号；
  `READ_REG`/`SET_BIT` 这类每个 DDL 头都有的公共宏必须排除，否则会得出"每个 .c 都要全部 26 个头"。
- 还要排除**结构体字段名**造成的假阳性（如 `Mode`、`timer`、`data`）。
- 补完 include 后跑**符号来源闭包**校验：对每个 `.c` 求 include 的传递闭包，
  确认它用到的每个 `DDL_*` / 寄存器 / `*_IRQn` / `extern` 变量都能在闭包里找到声明者。
  注意 `*_IRQn` 是 `enum` 成员、`SystemCoreClock` 是 `extern` 变量，
  只扫 `#define` 和函数原型会把它们误报成缺失。
- 结论同 L5：**能脚本验证的，就不许只靠阅读**。

## L8 新建骨架头前先查同模块是否已有遗留头

**现象**：批次 1 里我一边保留 legacy `bsp_pwm.h`（依据当时"legacy 不改名"的裁决），
一边又为同一个 ATMR 外设新建了骨架头 `drv_pwm.h`，`bsp_adc.h`/`drv_adc.h`、
`bsp_analog.h`/`drv_comp.h` 同理。Jovi 直接指出"否则出现 bsp_pwm.h 和 drv_pwm.h 重复"。

**根因**：把两条正确的规则各自套用，却没检查它们的交集——
「legacy 不做无收益改名」和「未落地驱动先建配置骨架头」单独看都对，
同时作用在**同一个外设**上就制造了重复头文件，比改名的代价大得多。

**规则**：
- 新建 `drv_xxx.h` 骨架前，必须先列出 `driver/inc` 全部文件，确认没有指向同一外设的 `bsp_xxx.h`。
- 若已存在，**不建骨架**，直接把冻结配置写进现有头并同步合并改名；宁可当场改名，也不留重复头。
- 模块归属按**真实外设**判断，不按文件名：OPA 属于比较器前端 → 合并进 `drv_comp.*`，不新建 `drv_opa.*`。
  判断依据优先查参考工程（aurora `drv_comp.h` 本身就声明 `BSP_OPA_Init`），不靠自己推测。
- 两代配置必须共存时，旧值加 `LEGACY` 段同文件分节存放，**禁止**为"统一"而改值——那是行为变更。

## L9 include 可解析性校验的索引范围必须覆盖整个仓库

**现象**：脚本检查「所有 `#include "..."` 目标可解析」报了 32 条 FAIL，
全是 `g32f031_ddl_*.h`、`g32f0xx.h`、`g32_assert.h` 这类明显存在的头文件。

**根因**：我把索引根设在 `Application/`，而 DDL 库在 `Application/` 之外。
索引范围小于引用范围 → 外部库头被全部误判为缺失。

**规则**：
- 可解析性校验的**索引根取仓库根**，引用扫描范围才是工程子目录，两者不能用同一个根。
- 这类"一眼假"的批量 FAIL（几十条全是知名系统/库头）先怀疑脚本，不要先怀疑代码，
  更不要据此去"修"include——与 L7 的假阳性同源：**扫描口径错了，不是代码错了**。
- 取符号做闭包比对前先剥离注释，否则注释里的旧名会被当成活引用。

**顺带**：目标工程是 git 仓库这件事本身就是最强的校验工具——
`git show HEAD:<path>` 取原文 → 折叠改名映射 → 去注释去 include 后比对令牌流，
可以字节级证明"纯改名、零逻辑变更"。改名类任务应默认先查 `git rev-parse --is-inside-work-tree`。

## L10 子代理的"已精确应用"报告不可作为交付证据

**事件**：haiku 执行器报告 8 处编辑全部精确落地；sonnet spec 审查随即发现两处**报告之外**的注释删改（MemManage 头注释被截短、drv_comp.h 少插 1 行且内容被改），且审查期间文件仍在变化（审查器两次 Read 结果不同）。已按字节规格修复并经控制器亲验 git diff 与 spec 完全一致。归因未定论——执行器否认，其 old_string 起点也确实无法触及被删行；可能是执行器未报告的额外编辑，也可能是并行进程/IDE 保存。

**Why**：子代理的自我报告是对自身行为的重构记忆，不是磁盘证据；小模型对"我做了什么"的自述尤其不可靠。文件在多进程（执行器、审查器、IDE）之间共享时，任何一方看到的中间态都可能是暂态。

**How to apply**：
1. 子代理任务完成后的验收以 `git diff` 为准，控制器亲自逐 hunk 核对，不采信执行器的自查输出。
2. 敏感文本（注释、文档）的编辑规格必须给到逐字节 old/new；执行后立即 diff。
3. 审查者若观察到"文件在变"，先停、冻结、全量重读，再下结论，不要基于暂态报告问题。
4. 同轮第二次派单中 haiku 在 old_string 不匹配时正确 BLOCKED 而非瞎猜——规格含"找不到就停"的显式指令时小模型可靠；规格含"凭理解改写中文"时不可靠。
