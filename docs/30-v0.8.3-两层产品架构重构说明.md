# 30 · v0.8.3 两层产品架构重构说明

## 1. 为什么再次调整目录

v0.8.0/v0.8.1的软件行为已经逐步稳定，但首方源码仍存在：

```text
app/
service/
board/
driver/
project/keil/
```

对于当前这类裸机单MCU产品，`service/`主要承担APP运行调度、ISR事件邮箱、PWM最终提交、Flash保存和看门狗健康监督；`board/`主要承担板级参数、ADC标定和功率门禁。继续把它们作为独立顶层层次，会导致：

1. 阅读工程时需要跨4个首方层定位一条控制链；
2. `app.h + service.h + project/keil/main.c`共同描述“应用怎么运行”，入口过于分散；
3. Board实质属于目标硬件适配，却和Driver分开；
4. MCU迁移时容易同时修改board/driver/service，边界反而不清晰；
5. 对Codex和人工维护而言，层次数量超过了当前产品规模真正需要的复杂度。

因此v0.8.3只做**架构收敛**：

> 生产代码严格收敛为 `APP → Driver → Vendor`。

这不是删掉旧Service的安全逻辑，而是把这些逻辑并入应用运行根；也不是删除Board能力，而是把它归入Driver。

## 4. APP层职责

### `app/src/main.c`

这是v0.8.3唯一产品运行根，合并：

```text
旧 app/src/app.c
+ 旧 service/service.c
+ 旧 project/keil/main.c
```

但“合并文件”不等于把所有事情写成God Function。

`main.c`内部仍保留清晰的static函数，例如：

- ADC完整块消费；
- UART事件消费；
- PWM命令落实；
- Relay实时二次复核；
- Flash Journal执行；
- Watchdog健康监督；
- 快速OCP恢复；
- 业务APP初始化与1ms调度。

因此它承担的是**运行编排**，各业务算法仍在各自模块。

### `app/src/interrupts.c`

从旧Keil目录迁入APP，因为中断桥接属于“产品如何使用Driver”，而不是Driver本身。

严格限制：

```text
Driver ISR状态读取/应答
→ 快速关PWM
→ 投递事件
```

不得直接调用：

```text
MPPT
Charger
Measurement完整换算
Flash编码
UI状态机
```

更重要的是，v0.8.3中 `interrupts.c` 不再包含 `g32f031_ddl_atmr.h`，共享ATMR向量是否有UPDATE事件由 `drv_pwm_update_isr_ack()` 在Driver内部判断。

### 业务模块

`charger/measurement/mppt/power_stage/protection/protocol/storage/ui`继续保持业务职责。它们不能直接调用Driver，避免两层架构退化成“所有APP文件都随便写硬件”。

## 5. Driver层职责

原Board层整体归入Driver：

```text
board/board_config.h  → driver/inc/board_config.h
board/board.h         → driver/inc/drv_board.h
board/board.c         → driver/src/drv_board.c
```

`drv_board`负责：

- ADC标定描述；
- 功率人工总门；
- Flash双页地址；
- 板级硬件配置封装。

Driver可以直接依赖：

```text
vendor/cmsis
vendor/device
vendor/ddl
```

但绝不能包含：

```text
main.h
app_config.h
app_types.h
charger.h
measurement.h
mppt.h
power_stage.h
protection.h
protocol.h
storage.h
ui.h
```

这让未来换MCU时仍能做到“优先替换Driver/Vendor”。

---

## 6. Driver头文件为什么拆分

v0.8.2以前只有一个较大的 `driver.h`。v0.8.3增加：

```text
drv_adc.h
drv_comp.h
drv_flash.h
drv_io.h
drv_pwm.h
drv_system.h
drv_uart.h
drv_watchdog.h
drv_board.h
```

`driver.h`仍保留为统一入口，只负责聚合这些接口。

这样：

- `main.c`可以简单包含`driver.h`；
- 以后某个模块如Debug只需精确依赖具体Driver时也有可选接口；
- 每类外设契约更容易审核；
- Driver源文件依然可以继续包含统一`driver.h`，无需为了目录调整大面积改实现代码。

## 7. Debug设计

新增：

```text
app/inc/debug.h
app/src/debug.c
```

当前：

```c
AURORA_DEBUG_ENABLE = 0
```

Debug默认无输出，不占用产品PA10/PA11 UART。

PB7/PB8虽然硬件预留为DEBUG TX/RX，但在真正建立独立Debug UART Driver和确认实时性之前，不允许为了打印方便直接占用产品通信口或在业务代码操作寄存器。

## 8. v0.8.1 PVD启动必须原样保留

两层重构不允许破坏：

```text
Reset
→ 最小GPIO安全态
→ HSI Ready
→ PVD Ready
→ VDD > VPVD
→ 连续稳定100ms
→ 才启动IWDT/PWM/COMP/ADC/UART/APP
```

PVD仍然：

- 默认2.8V候选；
- 不触发系统复位；
- 不启用PVD中断；
- 弱光低压不生成APP Fault；
- 中途掉压只把连续稳定计时清零。

具体依据继续见docs/28、docs/29。

## 9. 继电器安全链必须保持

架构变简单不代表安全复核可以删除。

`app/src/main.c`仍保留Relay二次实时复核：

```text
Power Stage先确认压差<=1.5V连续1s
→ 请求Relay ON
→ main.c先物理关PWM
→ 重新读取最新BST_U/BAT_U
→ 再检查Protection、pending fault和PWM实际状态
→ 才允许Driver真正写Relay GPIO
```

之后仍需：

```text
100ms机械稳定
→ 压差<=2.5V
→ PWM OFF
→ BAT_U完整10s max-min<=2V
→ RUN
```

## 10. 测试兼容文件的说明

为了保留已有大量Host行为回归，`tests/`中允许存在：

```text
tests/app.h
tests/service.h
tests/board.h
```

这些只是**测试兼容别名**，让旧测试用例逐步迁移；它们不进入Keil工程，也不代表生产架构仍存在Service/Board层。

生产目录和架构检查会明确拒绝 `service/`、`board/` 重新出现。

## 11. 架构门禁

`tools/check_architecture.py`新增硬规则：

- 根目录service/、board/、project/keil/必须不存在；
- APP/Driver文件集合必须符合v0.8.3定义；
- APP不得直接包含G32/DDL/board_config；
- 业务模块不得调用drv_*；
- Driver不得反向包含APP；
- 生产代码不得残留`aurora_service_*`、`aurora_board_*`；
- interrupts.c不得出现DDL或目标芯片寄存器访问；
- CMake和Keil不得引用旧目录；
- PWM preload/自然UEV/Automatic Output安全规则不得弱化。

---

## 12. 结论

v0.8.3的目的不是继续增加抽象，而是删除不必要的中间层：

```text
APP：产品怎么运行、怎么控制
Driver：硬件怎么执行
Vendor：芯片厂商基础库
```

软件安全逻辑仍然保留，只是从“Service是单独层”变为“main.c中的应用运行职责”。这更适合当前单MCU、裸机、固定功率拓扑的工程规模。
