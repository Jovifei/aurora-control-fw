# 02 · 软件分层与依赖规则

## 1. 单向依赖

```text
Application → Service → Driver Interface → Chip Driver → Board / Vendor
```

- `app/`只处理物理量、状态机和控制目标，不认识端口、通道、寄存器或芯片库；
- `service/`是唯一桥梁：ISR发布事件，主循环调用APP；APP输出逻辑命令，Service再调用驱动；
- `driver/`只实现外设语义，不认识MPPT、充电阶段或电池体系；
- `board/`保存PinMap、有效电平、分压比例、Flash地址和放行门禁；
- `vendor/`只提供CMSIS、器件定义和实际使用的DDL。

## 2. 功能文件职责

| 模块 | 只允许做什么 | 明确禁止 |
|---|---|---|
| measurement | 完整DMA块滤波、标定、物理量快照、BAT_I估算 | 发波、保护锁存、充电状态切换 |
| mppt | 更新Vpv_ref并计算理论功率 | 直接改Duty/CCR |
| charger | TC/CC/CV/Float和电池功率上限 | 访问ADC或GPIO |
| protection | 软件阈值、去抖、active/latched故障 | 恢复PWM |
| power_stage | 预充、继电器、Duty目标和状态 | 写寄存器 |
| service | 事件桥接、最终安全复查和驱动提交 | 实现MPPT/充电算法 |
| driver | 外设配置和最小ISR接口 | 包含业务头文件 |

## 3. 自动门禁

`tools/check_architecture.py`会拒绝：

- APP包含G32/Board/Driver/Service头文件；
- APP访问GPIO、ATMR、DMA、COMP或NVIC；
- Driver反向依赖业务层；
- APP/Driver/Service重新出现子目录；
- `legacy_*`、旧闭源库、BAT_S1/BAT_S2、JSON或重复tests/tools；
- APP重新碎片化成超过10个 `.c`；
- Service之外直接操作MOE；
- 运行期软件UG、AOE自动恢复或未启用CCR preload。
